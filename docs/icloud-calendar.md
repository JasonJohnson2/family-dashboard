# Apple iCloud Calendar — Phase 1

This is a read-only, server-side CalDAV adapter for one Apple Account in the existing private household. It feeds the same `calendar_sources`, `events` and `event_members` projections as Google and local plans. Imported occurrences appear in Calendar, Today at a Glance, upcoming events and member filters. Dashboard-created plans remain local. There are no Apple event writes, invitation responses, Reminders, Contacts, cron jobs or native app features.

## After Cloudflare deploys

The existing `pnpm deploy` pipeline applies new migration **0008_icloud_calendar.sql** before publishing the Worker. Do not run old SQL manually, reset the database or redeploy by hand. No new D1 binding is needed; `DB` remains the only database binding. The migration adds adapter metadata and leaves migrations 0001–0007 and existing Google/local/auth/Rewards data unchanged.

1. **Encryption setup:** if the Worker already has a valid `GOOGLE_TOKEN_ENCRYPTION_KEY`, iCloud can use that same secret with a separate authenticated encryption purpose. No extra secret is required. Alternatively, before connecting, configure **`ICLOUD_CREDENTIAL_ENCRYPTION_KEY`** as a Cloudflare Worker secret containing a cryptographically random 32-byte key encoded as standard base64 (44 characters ending in `=`). This dedicated key takes precedence. Never change which key is used for an existing connection without restoring the old key or re-entering the app-specific password. Generate a key with `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"`, then set it in Worker Settings → Variables and Secrets. Keep it out of GitHub, Wrangler vars and frontend environment variables. Local development uses a gitignored `.dev.vars` file. Existing household authentication and `REWARDS_OPERATOR_PIN` must already be configured.
2. Sign in to [Apple Account](https://account.apple.com/), enable two-factor authentication if needed, and open **Sign-In and Security → App-Specific Passwords → Generate an app-specific password**. Name it Family Dashboard. Copy the generated `xxxx-xxxx-xxxx-xxxx` password. **Never enter your normal Apple Account password.** See [Apple's instructions](https://support.apple.com/en-us/102654).
3. Sign in to the dashboard → **Calendar → Calendar connections → Unlock operator controls**. Enter your existing operator PIN.
4. Under **Apple iCloud Calendar**, enter the Apple Account email and **App-specific password**, then tap **Connect iCloud Calendar**. Discovery runs automatically. All discovered calendars are initially **disabled**, with Busy-only privacy.
5. For each desired calendar, enable **Show on dashboard**, select **Assigned to** (Everyone or any existing adult/child household member), choose **Privacy**, and tap **Save calendar**. Saving an enabled calendar requests a sync. Use **Sync calendars** to refresh all enabled external providers. No DevTools/API commands are needed.
6. Close Calendar connections and check the shared Calendar/Home views. Apple events are read only; edit them in Apple Calendar.

## Credentials and authorization

All CalDAV requests run in the Worker. The app-specific password is submitted once over the authenticated same-origin API. The uncontrolled password field is cleared before awaiting the submission; it is never stored in React state, browser storage, URLs or normal responses. Browser networking necessarily carries the initial submission. The server persists only AES-256-GCM ciphertext, a fresh 12-byte nonce and version. The shared credential engine preserves Google's exact v1 format, and iCloud uses distinct associated data `icloud-app-password:v1:home:<connection-id>`, preventing ciphertext substitution across connections/providers. Raw ICS is never stored.

Household authentication protects every settings, refresh and event API. Connecting, discovering calendars, changing settings, updating credentials and disconnecting require the existing session-bound operator token. Ordinary signed-in household users can view permitted events and refresh already-enabled providers. Member Adult/Child roles do not change Calendar privileges. The Google OAuth/PKCE/session checks, read-only scopes and management authorization are preserved. No admin key is entered into the frontend. API responses are private/no-store and credentials/provider error bodies are never logged. Existing automatic request logging remains disabled in Wrangler.

## Discovery and protocol safety

Discovery follows [RFC 6764](https://www.rfc-editor.org/rfc/rfc6764) / [CalDAV RFC 4791](https://www.rfc-editor.org/rfc/rfc4791): `.well-known/caldav` (root fallback on 404/405), `current-user-principal`, `calendar-home-set`, then Depth-1 calendar collection properties. It discovers collection URLs, names, colors, VEVENT support and advertised sync-collection support. Calendar URLs are not guessed from account names. Missing optional names/colors get safe defaults; Reminders-only collections are excluded.

The namespace-aware SAX parser accepts different prefixes/default namespaces and rejects DTD/entity declarations, malformed/truncated responses, failed required properties and oversized/deep documents. Relative hrefs resolve against the actual response URL. Credentials follow manual redirects only to HTTPS `caldav.icloud.com` or numbered `pNN-caldav.icloud.com` hosts, without URL credentials, custom ports, queries or fragments. Resource URLs must stay inside their collection. Other server hosts fail closed and need a reviewed adapter update, not a permissive URL override.

## Privacy and members

| Mode           | Persisted event details                                                      |
| -------------- | ---------------------------------------------------------------------------- |
| Busy only      | Times and generic Busy title; no source name in normal household projections |
| Title and time | Title and times; no location/description                                     |
| Full details   | Title, times, supported location and notes                                   |

Filtering occurs before event persistence. A privacy or enable/disable change immediately removes old projections and resource versions, resets the sync state, then imports the new permitted representation. This deliberately clears stale sensitive data even during outages. Settings/discovered calendar names remain operator-only; ordinary refresh status contains counts and safe categories, not account names/URLs/credentials.

One optional household-member mapping per external source is stored in `external_calendar_members`. It accepts existing adults and children equally and applies their existing identity/color through `event_members`. Mapping-only edits update differing assignments immediately without fetching Apple or clearing sync tokens. Foreign household member IDs are rejected. Everyone means the existing unassigned event behavior. Source-restricted SQL protects local/Google data from collisions and iCloud disconnects.

## Recurrence and sync

CalDAV multiget asks for server-side `calendar-data/expand` within the bounded window. `ical.js` parses returned RFC 5545 components and handles raw RRULE/RDATE/EXDATE, RECURRENCE-ID exceptions (including moved/cancelled occurrences) if the server returns unexpanded data. Explicit unsupported expansion responses use a raw-data fallback. Recurrence is projected as individual occurrences, not forced into the local calendar's simpler repeat presets. Embedded VTIMEZONE definitions are used; missing definitions for valid IANA TZIDs use Worker Intl conversion. Floating times use the household zone; all-day exclusive DTEND becomes the dashboard's inclusive end date. Actual instants preserve DST folds, and nonexistent/unsupported times fail the calendar batch rather than inventing times. Original recurrence identity, UID and resource address produce hashed, stable occurrence IDs.

The window is approximately **30 days past / 365 days future**, renewed after 30 days or a household timezone change, matching Google. Initial/reset sync gets a token **before** the bounded time-range query, so changes racing with that query are replayed next sync. When advertised, [RFC 6578 sync-collection](https://www.rfc-editor.org/rfc/rfc6578) returns changed/deleted hrefs and ETags. Only new/modified resources are fetched in multiget chunks. Invalid tokens or unsupported sync reports recover through a bounded ETag inventory, keeping cached events until a complete safe replacement is ready. Servers without tokens use that bounded ETag comparison on each due sync; unchanged resources aren't fetched or rewritten.

Only ETags and projected event ID lists are stored in `icloud_resources`; there is no raw ICS cache. Successful changes, resource metadata and tokens commit atomically under the shared fenced lease implementation, using separate provider leases. Failed/truncated reports never commit partial data or advance tokens. Recurring exceptions/deletions remove obsolete projected occurrences without deleting/reinserting entire calendars. Confirmed collection 404 or successful complete rediscovery removes only the affected iCloud collection.

## Refresh and D1 writes

Calendar renders cached household events first. Opening Calendar or returning focus/visibility/network requests a provider-neutral stale check. Home/ordinary household reads do not invoke sync. There is no minute polling or cron. Server staleness and ordinary retry intervals are one hour; manual refresh uses a one-minute cooldown. Revoked credentials stop further Apple attempts until reauthentication. A pending client request and a durable provider lease deduplicate simultaneous refreshes.

Fresh, disconnected, disabled and ordinary status/event reads write **zero** D1 rows. A legitimate sync writes a bounded attempt timestamp, lease/commit guards and success metadata. **No-change sync writes zero event/member rows and does not bump household revision.** Changed resources use bulk JSON SQL rather than one statement per object; changed event values/assignments are compared before writing. No balance/history/household-wide rewriting is added. Providers commit independently; aggregate refresh returns per-provider status so an iCloud failure never makes saved Google/local data unavailable.

The implementation limits response bodies to 2 MB, resource inventories to 1,000, projected occurrences to 10,000, raw recurrence iteration to 20,000 steps, CalDAV wall time to 90 seconds and individual HTTP requests to 15 seconds. A shared 40-external-request budget includes both providers, redirects and Google token exchanges. Exceeding limits preserves cached data. Very large calendars or complex raw recurrence can exceed [Cloudflare's free-tier CPU limits](https://developers.cloudflare.com/workers/platform/limits/); no local test proves production CPU entitlement. Prefer server expansion and a small set of household calendars, and inspect limits if Cloudflare reports Error 1102. V1 intentionally fails safely rather than running unbounded background work.

## Reconnect, disconnect and troubleshooting

- **Password rejected/revoked:** Generate a fresh app-specific password and use **Update app-specific password** for the same account. Cached events, enabled calendars, privacy and member mappings are retained. Apple revokes app-specific passwords when the main password is reset; see [Apple support](https://support.apple.com/en-us/102654). Sync marks authentication failures as requiring attention and stops repeated retries.
- **Account email:** Use the Apple Account that owns the iCloud calendars. Calendars stored only on an iPhone/Mac or another provider aren't in this iCloud account. Normal Apple passwords are rejected by the form/API shape; there is no second-factor dialog in the dashboard.
- **Secure storage setup message:** Restore/configure the encryption secret, then reconnect. Do not overwrite the existing Google encryption key to fix Apple; doing so breaks existing encrypted Google tokens.
- **Temporary outage, unsupported timezone, invalid XML, permission failure or timeout:** Keep cached data; retry after the cooldown or inspect the operator settings status. Server-side event expansion that times out or encounters a transport failure gets one raw-data retry, then remaining batches use raw data. If raw batches also fail in transport, reduce their size to ten resources, then fall back to individual read-only GET requests for the same validated Apple event-file URLs within the same 40-request/90-second limits. Retrieval must complete before any events or sync token are committed. Multiget omits the Depth header as specified by [CalDAV section 7.9](https://www.rfc-editor.org/rfc/rfc4791.html#section-7.9). GET fallback requires a complete HTTP 200 response, ETag and calendar body under the same safe redirect/body/credential checks. Missing individual files preserve the whole cached calendar rather than treating it as a deleted collection. If direct GET is rejected with HTTP 400, 405 or 501, retrieval switches to single-resource raw CalDAV REPORT for the rest of that invocation, without repeating unsupported GET. Each response must contain exactly the requested resource with its ETag and full calendar data. Authorization and missing-file errors do not trigger this compatibility retry. Direct download failures report `event-read`; single-resource REPORT failures report `event-report`. Collection metadata rows are excluded from event inventories, and collection URLs cannot be treated as event files. `icloud_timeout` identifies an aborted/timed-out request; `icloud_network` identifies other transport failures. No provider text or credential is included in errors. A permission error does not authorize deletion of cached events.
- **Sync diagnostic:** A failed refresh now shows an application-owned error code and sync step, plus the DAV HTTP status when available. Report these values (for example `icloud_response / event-download`), never your app-specific password or event contents. These details are returned only to authenticated household users and add no database writes. A Google warning retained from an earlier sync is identified separately from the current iCloud failure.
- **Missing new calendar:** Tap **Discover calendars**. Newly found calendars remain disabled until explicitly configured. A discovery failure keeps old settings intact.
- **Disconnect:** Confirm **Disconnect iCloud Calendar**. Removes iCloud ciphertext, resource/token state, owned projections, sources and member links. Does not revoke Apple's app-specific password remotely or alter Apple data. Revoke the password in Apple Account separately if no longer needed. Local/Google events and other household models remain untouched.
- **Different account:** Disconnect explicitly before connecting another; same-account credential updates preserve settings.

Automated tests use DAV XML/ICS fixtures and real local D1, never a live Apple account. Run `pnpm format:check`, `pnpm test`, `pnpm build`, `pnpm test:e2e` and `pnpm deploy:check` (dry-run only). Follow the README for local migrations and development. Real Apple server capability/permissions must be verified during household setup; V1 does not claim every Apple server variant or extremely old/high-frequency recurrence fits the bounded fallback.

Recommended later work: live-account compatibility feedback, resumable smaller sync batches for exceptionally large calendars, and richer provider settings/status presentation. Two-way Apple editing, additional accounts, invitations and continuous synchronization remain outside Phase 1.
